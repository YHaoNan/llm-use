# 总体规则
- 你应该生成markdown格式的文档
- 你应该生成结构化的文档：使用多篇文档进行组织，每一个文档中也分小节，详见“生成文档结构”一节

# 生成文档结构


- 概览：对代码库进行高度总结概括，不包含细节，目标是让人类可以对此建立一个整体性的了解
  - 文档结构：当前文档库的结构
  - 代码库的功能概述：描述本项目主要用于解决哪些问题，以及实现了哪些功能
  - 核心概念简述：介绍项目中核心的概念，方便用户理解后续的部分（如在探索VSCode的过程中Command是一个核心的抽象，你要介绍这些核心的抽象让用户有一个正确认识它的mental model）
  - 主要组件介绍：介绍项目中的主要构成组件，方便用户理解后续的部分
  - 架构设计：介绍项目的总体架构，包含主要组件以及组件之间的关系。除了文档描述外，应该使用PlantUML进行架构图的绘制
  - 系统入口点：从项目入口的视角贯穿主要流程。该章节并非所有类型的项目都需要，比如一个传统的SpringBoot后端项目，这个视角对于理解项目并没有任何帮助，工具类项目或具有明确流程的项目较为需要，请你评估后决定是否引入相关内容。
  - 其它的复杂且关键的技术架构、概念：非必要，只有当存在那些需要一个小节介绍的技术架构、概念，你应该在这一小节进行稍微详细的介绍，方便用户了解。你仍不应该包含细节，站在足够高的抽象层级上介绍。
  - 关键技术：总结项目中依赖的主要技术，方便用户快速了解项目的技术栈。
  - 目录结构：项目的目录结构，方便用户快速了解项目的组织方式。
  - 核心概念：此文档具体介绍所有核心概念，它应该是一个参考类型的工具文档，而非给用户的guide或tutorial
    - 如何联系：首先介绍多个核心概念之间如何共同协作，你可以使用PlantUML进行组件图绘制
    - 每一个核心概念的独立介绍
      - 简要介绍
      - 主要职责
    - 快速开始：此文档是一个使用层面的用户指南，描述用户如何最快的将该项目跑起来，对于该文档你有足够的灵活性，如果项目很简单，你可以使用一个文档覆盖所有内容，反之，你可以生成多个文档，甚至每一种具体运行/编译方式，甚至其中的一个小节（如安装环境、依赖）都是独立的文档
      - 启动：用户如何快速的运行该项目，如果有多种运行方式，你应该生成平行的多个快速运行小节（如，启动（Docker），启动（本地）等），对于每一种运行方式，你可能需要使用多个子小节来完整的向用户介绍
      - 配置：项目的配置项，哪些文件是配置，有哪些配置方式，配置文件，命令行参数，环境变量，配置中心，它们之间的优先级。
      - 编译细节：对于像CMake这种复杂的构建系统，或使用多种语言的项目，典型的是基于Rust/C++/Python等技术协同开发的操作系统，你应该详细的介绍如何构建项目，包括准备环境，安装依赖，各种脚本介绍（如CMake，Makefile等），以及如何具体的编译项目。遵循金字塔模型。
      - CI/CD流程：如果项目包含完整的CI/CD规范（常见于企业级项目），你应该有一个文档详细的介绍它
- 具体模块文档
  - 对于足够复杂的子模块，你应该独立的生成它的细节文档/文档集，它的文档结构应该和概览结构差不多，只不过它聚焦于当前模块的具体细节，如它的核心概念、主要组件、架构设计等文档都聚焦在当前模块的边界内
  - 扩充：概览聚焦于高抽象层次的整体介绍，而具体模块中除了保持概览的整体结构外，可能需要包含如下额外内容：
    - 数据模型介绍：常见于后端项目，介绍当前模块的数据建模，可以使用PlantUML绘制ER图
    - 用例介绍：当前模块的主要用例，可以使用PlantUML绘制用例图
    - 关键流程介绍：当前模块的关键流程，你可以使用PlantUML绘制时序图或流程图
    

> 对于这份文档结构，你有足够的自由度进行扩展，有足够的自由度决定它们如何组织。但是你需要遵循如下的文件组织方式限制：
> - 目录（如概览）
>   - Index.md（主文档，用户点击这个目录时，实际上需要展示这个文档）
>   - Other-Doc.md（其它文档，下挂在这个目录下的其它文档）
>   - Other-Dir（其它目录，下挂在当前目录的其它目录）
> - Doc.md（直接文档）
>
> 核心：使用目录组织多文档，目录下Index.md是目录需要展示的内容，目录中可以包含其它文档或目录，它们的展示顺序可以根据你的需要进行调整。

# 总体限制
- 金字塔模型：你的文档生成应该遵循金字塔模型，循序渐进的向用户披露更多信息，而不是平铺式的展示所有内容
- 善用绘图：你应该在文档中善用PlantUML进行绘图，如用例图，架构图，时序图，组件图，流程图，ER关系图等，每次生成一个图，必须调用plantuml_validate_mcp工具进行校验，你需要利用返回的信息判断你的生成语法是否正确，若错误，你需要修正它。
- 文档之间的关联：你应该在文档中利用标准markdown的链接语法构建文档之间的关联
